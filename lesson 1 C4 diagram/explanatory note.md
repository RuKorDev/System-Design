# Архитектура платежной системы

## Общий обзор
Система обработки платежей обеспечивает:
1. Клиентский доступ к платежным операциям
2. Обработку и управление платежными транзакциями
3. Проверку транзакций через Anti-Fraud систему
4. Сбор и анализ данных о платежных операциях


## 1. Выбор Gateway (Kong)
**Роль**: Единая точка входа для внешних запросов

**Выбор технологии**: Kong
- Простая интеграция с Keycloak для аутентификации
- Nginx-based (высокая производительность)
- Настройка load balancing и rate limiting
- Автоматическая генерация `request_id` в формате UUIDv7 для трассировки

## 2. Взаимодействия

**Прием платежей**:
1. `Gateway` -> `Payment initiator service`  (REST) - перенаправление входящего запроса на обработку платежа
   - **Выбор REST**: для внешних интеграций и синхронного ответа что платеж взят в обработку или отклонен 
2. `Payment initiator service` -> `Wallet Service` (gRPC) - проверка баланса, резервация средств
    - **Выбор gRPC**: возможность мгновенно вернуть ошибку при недостатке средств
3. `Payment initiator service` ->  `Payment Executor Service` (Kafka) - отправка платежа в обработку если сумма операции не требует проверки на антифрод
    - **Выбор Kafka(topic `to_payment_executor`)**: асинхронная обработка с единной шиной данных
4. `Payment initiator service` ->  `Anti Fraud Service` (Kafka) -  проверка на антифрод
    - **Выбор Kafka**: не заставлять клиента ждать, платеж уже принят в обработку
5. `Anti Fraud Service` -> `Payment Executor Service` (Kafka) - отправка платежа в обработку 
    - **Выбор Kafka(topic `to_payment_executor`)**: асинхронная обработка с единной шиной данных
6. `Payment Executor Service`  -> `Sbp adapter, Card processing adapter, Core integration adapter` (Kafka) - обработка платежа
    - **Выбор Kafka(topic `from_payment_executor`)**: сообщения идут в один топик потребитель сам решает на основе сообщения
      необходимо его брать в обработку или нет
7. `Sbp adapter, Card processing adapter, Core integration adapter` -> `Payment Executor Service` (Kafka) -  результат платежа 
    - **Выбор Kafka(topic `from_adapter`)**: без паттерна outbox достаточно обеспечить гарантию доставки at least once
8. `Payment Executor Service`  -> `Notification service/ Payment history service/Wallet Service` - сохранения платежа в терминальном статусе, нотификации об этом пользователя, списание заререзвированных средств
    - **Выбор Kafka(topic `executed_payment`)**: сообщения идут в один топик, потребители действуют согласно своей логике

**Отображение истории платежей и баланса пользователя**:
1. `Gateway` -> `Bff service`  (REST) - перенаправление входящего запроса
2. `Bff service`  -> `Wallet Service` (REST) - информация о текущем балансе пользователя
3. `Bff service`  -> `Payment history service` (REST) - история платежей
- **Выбор REST**: для внешних интеграций и синхронного ответа  (тк более просто использовать и поддерживать, и подходит по ожидаемой нагрузке)

## 3. Kafka vs RabbitMQ
**Выбор Kafka в проекте обусловлен**:
1. Высокая пропускная способность
2. Использование как единой шиной данных, в проекте имеются топики у которых несколько групп потребителей.
3. Лучшее масштабирование

## 4.Переход на UUIDv7

### План обеспечения бесшовного перехода от bigint к UUIDv7:
1. определить срок перехода (в зависимости от требований бизнеса сколько максимально может находиться платеж в обработке и тд)
2. на время перехода обеспечить поддержку обоих форматов (для новых платежей создать другую схему с таблицами)
3. в старой таблице добавить новое поле с UUIDv7 и при миграции данных  в хранилище использовать его (но с сохранением старого id)
4. на время перехода с помощью конфигов и фича флагов определять из какой схемы брать данные, после окончания переходного периода выключить фича флаг

### Преимущества перехода на UUIDv7:
1. автоматичесмкая генерация в каждом сервисе
2. привязка ко времени
3. стандартный uuid формат
4. хорошая производительность

### Недостатки перехода на UUIDv7:
1. сложности во время перехода
2. размер uuid (128 бит) в 2 раза больше чем BIGINT
